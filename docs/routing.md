# 总控路由与运行环境

真实入口为 `POST /api/messages` → `Runtime.receive/process` → `model.route` → 本地协议校验与执行者分配 → 任务动作。普通后台使用真实模型和执行适配器；显式注入验收依赖的后台标记为 test，桌面持续展示测试标识。

## 对话与目标范围

总控返回 `{ reply, actions }`，动作集合为 create、supplement、status、stop、clarify。问候、咨询和讨论直接回答；明确委派目标才执行。创建、追加、停止、查询和澄清的反馈由 Runtime 生成，有动作时不展示模型预先声称“已经完成”的回复。

模型上下文将用户选中的任务、最近有关联的对话、同目录任务与其他目录任务分开。工作目录和用户目标共同确定任务范围：同名目标位于不同项目时不能自动视为同一任务；补充约束不能降级成状态查询；没有明确目标或唯一关联时，“那个先停一下”应澄清，不扩大为停止所有任务。

每条消息在本地选取最多 12 项任务。优先保留选中或按编号、完整标题点名的任务，再考虑最近关联、当前项目和其他活跃任务。已完成、已取消和失败的任务默认留在本机；查历史时可按标题关键词召回，接着说“刚才那个”也能关联上次讨论的任务。候选不完整时，模糊或批量的任务变更会要求明确目标。相同目录的重复创建仍在本地全量核对。

最近关联从末尾 24 条消息查找，发给模型的对话最多 8 条，并限制单条长度。纯问候不带任务清单或旧对话。路由只传当前目录的分配偏好、少量计划和会话摘要，不带任务执行结果、计划正文或历史报告全文。只读状态查询仍由本机后台读取实际数据。最近讨论原生任务时不会退回更早的 ACD 执行任务作为默认目标；原生会话不能通过这套路由追加或停止。

## 执行者分配

总控仍只进行一次结构化模型请求。`create.agentId` 是模型建议；Runtime 通过本地策略决定最终执行者，优先级为：本次明确指定 → 项目默认 → 全局默认 → 唯一合格候选 → 合法模型建议。所有选择先满足已接入、可用、已适配和必要协议能力。多个候选而模型建议无效时明确反馈，不按候选数组顺序随意选择。

桌面输入区可明确选择下一条消息立即新建任务的执行者，CLI 使用 `acd send "要求" --agent <编号>`。请求增加 `targetAgentId`，本地代码将其作为硬约束；不可用或能力不符时保留消息并反馈，不静默改派。正文明确点名时由模型提取 `create.requestedAgentId`，同样优先于默认偏好；自然语言提取质量仍依赖总控模型，结构化选择优先。没有明确点名时不能从历史或品牌认知虚构指定。已有任务的补充保留原 Agent 与原生会话，这些字段不承担改派功能。

`requiredCapabilities` 可选择 `steer`（执行中追加）、`resume`（会话续接）、`approval`（原生授权交互）、`input`（普通文字输入）。适配器提供能力事实，不声明代码、文档等任务质量专长。模型只有在本条要求明确提出对应能力时才填入 create 的必要能力；Runtime 合并消息结构化选择与动作要求，不能删除用户已选择的能力。支持交互不表示支持所有原生请求类型，也不授予工具权限。任务启动前重新检查已分配执行者，不满足时阻塞并反馈，保持原分配。

默认偏好通过 `GET /api/allocation` 读取，`PUT /api/allocation` 保存，返回 `AllocationSettings`：`{globalAgentId, projectAgentIds}`。PUT 正文为 `{agentId: string|null, projectPath?: string}`；省略目录更新全局，提供目录则规范化到真实项目路径，null 清除对应偏好。默认只允许选择已接入且可用的执行端；后来失效的默认可被跳过，选择原因中说明。CLI 使用 `acd agents default <编号|none> [--project <目录>]`，不带参数查看当前配置。

Task 的 `allocation` 保存策略版本、来源、必要能力、模型建议和候选排除原因；详情显示本地生成的分配依据，不保存模型内部推理。偏好存入现有 SQLite settings，消息选项进入原消息日志并参与幂等检查，重试与澄清保留选择；能力数组按集合规范化。旧任务、旧消息和 v1 草稿保持兼容，新客户端在旧后台缺少 `agent-allocation` 能力时拒绝提交新选项。

定时计划仍在“定时任务”页面配置固定执行者；本次执行者/能力选项用于立即新任务，带这些选项的自然语言定时创建会明确拒绝并保留消息，避免忽略选择。

此策略不提供按成本或质量评分、负载均衡、并发上限、自动改派或 worktree。目录冲突仍由现有 Runtime 控制；不能通过更换执行者绕过同目录等待。启动检查不等于账号或模型权限已验证。

## 本地约束

- 由 Zod 校验动作结构。新任务目录绑定本条消息的规范化 cwd，模型不能生成其他目录。
- 追加与停止的 expectedRevision 来自发起请求时的任务快照；执行前再次核对。模型不能生成版本号，也不能把用户明确选中的 taskId 改为另一项。
- 同目录已有同标题的未结束或待检查任务时，意外 create 转为澄清，避免直接重复执行。模型判断可以并行；Runtime 在每个 create 落地前再核对当前任务。同一批动作或两条并发消息发生碰撞时，先创建的任务保留，后续动作进入澄清，原消息收据也记录澄清。用户明确要求独立另开时仍可创建，同名不同目录也不冲突。这只是标题碰撞保护，语义相近但标题不同的识别仍依赖模型。
- 执行端、目录、任务存在性和当前状态仍由 Runtime 核验。请求失败或格式不合法不会降级为创建任务，未确认操作不自动重放。
- 多条消息立即接收，可同时理解；独立目录可并行执行，相同或父子目录保守等待。

澄清支持选择任务或自由文字回答；从完整消息索引取回原要求。原生授权仍只能使用给定选项。

## 理解状态

用户消息保存独立 `routing` 收据：pending 为理解中，completed 表示返回了合法决策，failed 为请求或协议失败，interrupted 表示服务重启打断了理解。收据不代表任务执行成功；failed/interrupted 不自动重放。失败或中断且尚未应用动作的原消息，可以显式“重新判断”；网络重发、理解重试和执行恢复的区别见 [消息恢复](message-recovery.md)。

总控上下文只提供已选择可用执行者、任务元信息、待处理问题和近期对话；原生任务只来自当前观测范围。空 ACD 任务列表不代表其他原生实例没有工作。

## Ollama 与可重复验收

本机 Ollama 使用严格 JSON Schema、`reasoning_effort: "none"`、温度 0 和最多 2,048 输出 token，仍保留超时、输出截断检查与本地 Zod 校验。执行 Agent 使用各自配置。参考 [Ollama 结构化输出](https://docs.ollama.com/capabilities/structured-outputs)。

固定语义案例保存在 `tests/routing-cases.ts`，包含多候选明确指定、候选反序和显式协议能力案例。分配优先级、默认失效、硬约束、幂等及持久化另由 Fake Runtime/HTTP 测试验证。手动验收仅调用本机模型，使用合成任务，不启动执行 Agent，不读取实际会话或业务文件；普通 `npm test` 不运行这些模型请求。

```sh
npm run eval:routing -- --model qwen3.5:4b-q4_K_M --repeat 2
```

可指定已安装模型；每项记录动作、目标、版本、用时和错误，结果保存到系统临时目录。输出路径在终端显示，失败以非零状态结束。

2026-11-03，本机 Qwen 首次检查暴露了模糊停止扩大范围、跨目录错复用以及重复目标误新建。修复后 14 个固定案例连续两轮 28/28 通过，覆盖问候、讨论、空任务查询、重复目标、独立同名任务、指定目标、模糊停止、最近任务补充、跨目录、新约束、否定全部和明确全部停止。

上述 28/28 是新增分配策略之前的历史记录，单候选案例不证明多 Agent 择优；新增多候选语义案例需另行运行，普通测试只验证隔离协议与本地规则。

这些是有限模型案例；其他型号和未覆盖的自然语言仍需独立验收。创建任务的真实执行、追加、停止和授权也需要分别验证，不能以路由分数代替执行闭环。已完成的一次真实 Codex 文件任务和结果汇报见 [试用记录](dogfood-2026-11-03.md)。
