# 上下文补查与 Agent 核实实现计划

用户已确认先读取关联任务历史，再向原执行 Agent 核实的流程。实现复用 Store、路由和 Task 生命周期。

## 设计

总控新增 history 和 ask_agent 两种结构化动作。用户追问缺少事实依据时，history 只读取本地保存的对话、任务结果及交付报告。按目标编号、内容相关性和最近关联排序，返回带来源的有限公开片段。模型最多再判断一次，回答、澄清或请求 Agent 核实。

ask_agent 只能引用本次历史结果里的执行来源。创建 responseKind 为 answer 的核实 Task，保留原消息关联和原执行者。Codex 从原会话 fork 独立只读会话，禁止审批与写操作。核实目标只使用本轮问题和明确来源，不重新下发原工作要求。原会话和执行者无法定位时澄清，适配器不支持核实时明确说明。状态不确定的核实不自动重试。

常规创建、补充、停止和定时任务契约继续使用。最近原生交付报告作为有界来源锚点进入路由上下文。查询历史不产生工作任务，只有实际询问执行者才创建可观测的核实 Task。

## 文件与验证

- contracts/investigation.ts 定义有来源的查询结果。contracts/index.ts 增加动作和可选 inquiry 字段。
- core/history.ts 选择并脱敏历史片段。以模拟的跨目录任务、同名任务、历史报告和未知结果验证来源与裁剪。
- core/model.ts 加入有界调查协议与回复提示。core/runtime.ts 串联历史检索和现有任务执行，验证重复查询不会循环或重复执行。
- core/adapters/codex.ts 使用原协议的只读 fork 入口，验证原会话不被 resume、无写权限、原始工作指令不重新提交。
- routing-context.ts 保留最近原生报告关联，验证简短追问可获取来源锚点。
- 同步路由、执行适配器和架构文档。运行受影响测试、完整测试和构建，再交付包含任务结束修复的安装包。
