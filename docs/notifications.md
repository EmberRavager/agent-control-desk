# 消息提醒

消息中心、桌面通知和微信同步各有明确职责：消息中心保存关键事件与未读状态；桌面通知在应用后台提示；微信按个人微信设置回传。点击提醒只定位上下文，不会替用户批准操作。

## 使用方式

- 左下角铃铛进入消息中心，角标显示未读数量。点击记录可定位到任务、问题或近期消息。原报告已移出最近 200 条聊天记录，或同一会话已生成新报告时，点击旧通知会打开对应的历史报告全文与建议。
- 设置 → 消息提醒：桌面通知、声音、是否显示任务名称和摘要、关闭窗口后驻留，以及三类桌面提醒开关。默认隐藏任务详情。
- 设置中可以发送测试通知、查看最近系统反馈，并打开系统通知设置。系统支持通知不等于已授权；系统专注模式也可能影响横幅和声音。
- 微信提醒仍在“设置 → 个人微信”中单独管理。

```sh
acd inbox
acd inbox --json
acd inbox read <消息编号>
acd inbox read-all
```

## 提醒规则

| 事件                             | 行为                         |
| -------------------------------- | ---------------------------- |
| 授权或澄清问题                   | 需要处理提醒，点击定位原问题 |
| 模型判定用户委托已交付           | 一份完成报告对应一条结果提醒 |
| 旧任务进入 review 且没有判定记录 | 提醒人工检查                 |
| 失败、阻塞、状态未知             | 异常提醒，点击查看任务       |
| 总控缺配置、凭证失效或路由失败   | 留下关联总控消息的提醒       |
| 普通进度、逐字输出、重复快照     | 不生成重复提醒               |
| 用户自己确认完成或停止           | 不额外重复弹窗               |

新任务执行结束后先判定是否交付。等待判定、判定失败或尚未交付的任务不会产生完成报告通知。旧版本已经创建的占位提醒在报告就绪后更新正文，保留原有已读和桌面领取状态。见 [结果汇报](completion-reports.md)。

相同问题或同一轮任务状态只保存一次。短时间多条提醒合并成一条系统提示；正在前台使用 ACD 时，只保留消息中心记录。连续输出不会不断重置提醒等待时间。

“全部已读”使用点击时的消息序号作为水位；操作期间到达的新消息保留未读。记录按持久序号排序，不依赖系统时钟是否回拨。已读只表示看过，不表示任务已经完成或授权已经通过。

## 关闭、退出和后台

默认关闭窗口时隐藏到菜单栏/托盘，桌面进程保持订阅以接收提醒；可以从菜单重新打开。关闭此选项或托盘不可用时，关闭窗口会退出桌面进程。

托盘菜单“退出桌面端（后台任务继续）”明确退出 Electron，本地任务服务与已启用的微信仍可继续运行。退出桌面进程之后，不再即时弹出系统通知，关键事件仍保存到消息中心。电脑睡眠或关机时无法继续运行。

桌面端仅在本次启动的首次连接时尝试启动后台。用户主动停止后台后，桌面重连不会重新拉起它；运行 `acd service start` 或重新打开 ACD 才会恢复，任务不会自动重跑。

## 持久化与本机接口

消息投影复用 Runtime 和 Store，SQLite 的 `notifications` 实体保存事件、已读和桌面领取状态；独立序号避免同时到达或时钟变化破坏已读水位。设置保存在同一数据目录，不增加另一套任务系统。

- `GET /api/notifications`：最新 50 条、未读数及设置；可传 `?before=<消息编号>` 分页。
- `GET /api/notifications/<消息编号>/report` 返回该通知对应的完整就绪报告。缺失的报告或已排除的内部会话返回 404。桌面能力标识为 `notification-report-detail`。
- `PUT /api/notifications/preferences`：保存完整提醒设置。
- `POST /api/notifications/read`：`{ ids }` 或 `{ throughId }` 标记已读。
- `POST /api/notifications/claim`：领取符合当前设置、未读且仍有效的提醒。
- `POST /api/notifications/settle`：记录提交、失败或抑制结果。

以上接口沿用本机认证、请求大小限制、桌面 IPC 白名单和能力检查。领取在系统通知提交之前持久化；重连和重启不会重复领取。系统无确认回执时保存为 `unverified`，不再误记 `submitted`；领取后崩溃或系统结果不明时不盲目重发，消息中心仍保留记录。系统通知的提交/显示事件不能当作用户已经看到或读过。

## 平台与验证边界

在仓库根目录运行 `node --import tsx scripts/verify-report-notice-ui.mjs /path/to/installed/jsdom` 可复验历史报告入口。脚本通过当前桌面渲染器点击消息中心，验证同一会话在 205 条新消息后仍可打开旧报告全文和建议。使用临时数据库、回环 HTTP 接口及模拟桌面 bridge。

使用 Electron main-process Notification API，保持 renderer 权限关闭。系统设置入口使用固定 URI，renderer 不能传任意外部地址。

[Electron 官方说明](https://www.electronjs.org/docs/latest/tutorial/notifications)要求 macOS 通知使用已签名应用，Windows 通知需要对应应用标识与快捷方式注册。当前已设置 Windows 应用标识和激活标识，但正式安装注册、签名包与 Windows 实机验证仍未交付。源码开发时，系统中显示的应用名称也可能是 Electron。

已通过隔离测试验证状态生成、去重、并发领取、已读水位、分页、重启、通知合并、隐私与声音选项、点击目标、托盘生命周期和系统设置入口。界面通过 13 个模拟 bridge 交互流程，并在浏览器中检查了默认宽度及 760px 最小桌面宽度的布局和点击定位。Mac 解锁后，已在原生桌面点击“发送测试通知”，系统返回提交失败；真实横幅、声音与点击唤回尚未通过，具体的权限与开发应用签名影响仍待定位。不能把 Fake Notification 测试视为系统验收。
