# ACD 架构能力检查与优化（2026-11-04）

当前本地单后台、统一 Runtime、SQLite/JSONL 存储与原生 Agent 适配器的边界可以继续使用。本轮没有发现需要引入另一套任务执行器、恢复系统或大型重构的证据。检查确认并修复三项正确性问题，并删除状态发布中的重复计算。

审查针对当前实现。仓库源码均为未跟踪文件，没有可用于判断回归的提交基线，因此不将这些问题描述为某次提交新引入。验证使用临时目录、Fake Agent 和隔离后台；没有读取真实业务数据、配置或凭证，也没有重启当前安装版。

## 发现与处理

| 优先级 | 已确认问题                             | 触发与影响                                                                             | 本轮处理                                                                                           |
| ------ | -------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| P2     | `..` 前缀的合法子目录漏过互斥          | 父目录与 `..nested` 子目录的任务可以同时启动，破坏目录串行约定                         | 按完整的父路径片段判断，兼容平台分隔符；保留相邻目录并行                                           |
| P2     | 排队期间目录被替换，启动时使用错误目录 | 子目录排队后被替换为指向其他目录的符号链接；释放父任务后，两个执行可能落在同一真实目录 | 实际启动前重新验证 `realpath` 和目录类型；变化或不可访问时标记 `blocked`，不提交执行、不静默改目录 |
| P2     | 旧报告退出显示窗口后恢复未读与弹窗资格 | 同一原生会话的报告都滚出最近 200 条消息时，旧报告不再被认定为已替代                    | 在已有完整消息索引旁维护每个原生会话的最新报告 ID；日志重载与增量写入共用更新逻辑                  |
| 优化   | 一次状态发布构建两份完整快照           | 每段进展都重复读取实体、映射状态和构建通知列表                                         | 只读一次基础状态，投影通知后派生一次通知列表，再发布同一快照                                       |

目录检查保证启动这一时点与保存路径一致，不声称能防止同一操作系统账户下外部进程在检查后继续修改目录。

## 架构能力与边界

| 能力                     | 当前判断                                            | 仍需保留的边界                                   |
| ------------------------ | --------------------------------------------------- | ------------------------------------------------ |
| CLI、桌面、微信统一入口  | 共用消息、任务和持久化契约，职责成立                | 渠道到达、执行端收到和业务完成是不同事实         |
| 总控路由与本地执行者分配 | 模型建议经本地校验；明确选择和必要能力由本地约束    | 不能以启动检查代替登录、模型额度或业务正确性验证 |
| 原生执行适配             | Codex、Claude Code、OpenCode、Pi 使用已有适配器入口 | 不同协议的追加、授权、输入能力仍有差别           |
| 队列与目录互斥           | 可以沿用；本轮修正两个目录边界                      | 不提供外部业务资源锁、自动 worktree 或修改合并   |
| 定时任务                 | 复用 Runtime 和事务，未发现需要另建执行体系的证据   | 运行依赖本机；错过不补跑；同计划前轮未结束不叠加 |
| 恢复与未知结果           | 保留 `unknown`、人工核对和幂等收据，属于必要保护    | 不把重启后的任务标记为成功，不盲目重放外部效果   |
| 结果与通知               | 原始结果、AI 报告和通知分开；本轮修复历史窗口依赖   | 模型报告成功不是业务验收，通知提交不是用户已收到 |

## 五步简化记录

本轮的具体请求人为用户；历史能力没有完整的具名需求记录，不补造历史提出人。表中的约束来源标明为现有契约。正确性、安全与未知副作用保护不因缺少历史署名而删除。

| #   | 原始需求/环节                            | 提出人                             | 不做会怎样                                   | 第1步结论                  | 第2步动作        | 第3步简化                        | 第4步加速                        | 第5步自动化              | 状态 |
| --- | ---------------------------------------- | ---------------------------------- | -------------------------------------------- | -------------------------- | ---------------- | -------------------------------- | -------------------------------- | ------------------------ | ---- |
| 1   | 一次发布重建两次完整状态                 | 来源未具名，属于实现细节           | 删除第二次读取后仍可发布完整状态             | 非必要重复                 | 删除重复读取     | 基础状态与通知派生分开           | 各基础实体每次发布读取一次       | 无需新增                 | 删除 |
| 2   | 用最近 200 条显示消息判断报告替代关系    | 来源未具名，属于实现细节           | 历史滚出后旧通知重新激活                     | 截断窗口不适合作完整性依据 | 删除显示窗口依赖 | 复用完整消息索引的最新报告 ID    | 常规报告更新和查询不扫描全部对话 | 日志重载复用同一更新逻辑 | 简化 |
| 3   | 父子目录互斥与执行前目录核验             | 既有架构契约，历史提出人未具名     | 并行修改相同真实目录，或进入变化后的目录     | 正确性约束必须保留         | 保留保护         | 修正路径片段判断，沿用 `blocked` | 相邻目录继续并行                 | 入队后启动前自动复核     | 保留 |
| 4   | 未知结果人工核对、授权过期、业务结果检查 | 既有生命周期契约，历史提出人未具名 | 无法确认的执行可能重复，或把退出当成业务完成 | 正确性与安全约束必须保留   | 不删除           | 沿用现有状态和入口               | 本轮不改变等待语义               | 不增加自动重试           | 保留 |
| 5   | 为扩展性拆出第二套调度或恢复体系         | 没有明确提出人或验收需求           | 本轮修复不依赖它                             | 当前需求不成立             | 从本轮方案排除   | 使用既有 Runtime、Store、Adapter | 避免新增集成交接                 | 不实施                   | 删除 |

**删除清单：** 删除一次状态发布中的第二份基础快照和第二次通知列表计算；删除通知判断对最近 200 条显示窗口的依赖；排除新增平行调度或恢复系统。可能的反对理由是担心通知陈旧或未来扩展受限：本轮测试确认新通知进入同一次发布，当前扩展点仍保留。没有删除产品功能或用户数据。

**最终保留清单：** 保留统一 Runtime、既有 SQLite/JSONL 日志、四种执行适配器、计划与执行任务分离、目录互斥、`unknown` 人工核对及结果检查。这些机制分别承担状态一致、持久化、协议边界、触发审计和不可确认效果保护。

## 验证与后续范围

新增六个针对性回归用例。修复前，两个 `..nested` 方向、排队目录重定向、报告退出窗口、重复实体读取共五个断言失败；相邻目录并行的控制用例通过。修复后六个用例通过，另验证旧报告更新、重启和身份替换不会改变最新报告的正确归属。

本轮完整回归 270 项通过（252 项 TypeScript 测试、18 项桌面端测试），构建与类型检查通过。没有把本地测试视为安装版或真实模型验收；当前运行的安装版未在这轮检查中替换或重启。

以下是后续候选，未作为本轮缺陷修复或擅自扩展：

- **历史规模：** 当前 SSE 仍发送完整任务快照，实体与日志的历史规模继续增长。分页、结果按需读取和历史压缩应先用脱敏的规模与耗时数据确定目标，再共同调整 HTTP、SSE、CLI 与界面契约。
- **能力声明：** 发现目录、默认能力与适配器工厂存在多处声明，目前支持的四种执行端值一致。新增执行端时应统一核对或集中定义；本轮不因潜在维护风险重构全部注册机制。
- **真实验收：** 长期定时执行、休眠唤醒、更多模型时间表达及跨平台行为仍需分别验证。
